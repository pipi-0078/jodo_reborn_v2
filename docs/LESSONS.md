## 1. 環境の限界(できないこと)

| できないこと | 詳細 | 対処 |
|---|---|---|
| GPU レンダリング | コンテナに GPU がない。Blender(bpy)は EGL がなく **render 不可**。Cycles の AO ベイクは最初のマテリアルにしか書けない | 見た目の確認は Vite ビルド + Playwright(swiftshader)で撮る。重いシーンはスクリーンショットに数分かかる(`timeout: 240000` を付ける) |
| 外部の 3D 生成 API | egress proxy が api.meshy.ai / api.tripo3d.ai / huggingface.co を遮断(npm・pypi のみ許可)。torch も入らない | image-to-3D は **施主が Tripo 等で生成**し、GLB を受け取って仕上げる |
| GitHub Actions の確認 | `actions_list` は 1 回で 7万〜29万文字返す | 呼ばない。プッシュ成功をもってデプロイ確認とする |
| 大きな画像の目視 | 1280x800 の PNG は約 1,365 トークン | 必ず `tools/inspect.sh <png> 640` で縮小してから見る。施主へ送る画像は縮小しない |
| コンテナの永続性 | 使い捨て。bpy / node_modules は消える | `pip install bpy pillow numpy && npm ci` で復元。http.server も落ちるので撮影前に `curl` で生存確認 |
| 別リポジトリ(jodo_diary)への書き込み | セッションの GitHub 権限は開始時のリポジトリだけ。私からの `add_repo` は自動モードの判定で遮断される(9/3) | 施主に「jodo_diary を追加して」と**施主の言葉で**言ってもらうと通る(9/4)。通ったら `git clone --depth 1` → `register_repo_root` |
| メイン空間の撮影時間 | 水面反射でシーンを 2 回描くため、swiftshader では 1 枚 3〜5 分 | `timeout: 600000`。複数枚は PORT を変えて並列に撮る。ビルド中に撮るなら `dist` をコピーして `DIST=` で別配信 |

## 2. アセット制作(Blender / bpy)での失敗

### 2-1. 手作りの造形は施主の期待に届かない
- 最初の木(プリミティブの寄せ集め)は「ファミコン以下」と言われ全削除(8/16)
- メタボールで自作した阿弥陀像は「ふざけてる?? ひどすぎるよ」で即却下(8/29)
- **教訓**: 有機的な造形(木・仏像・顔)はゼロから作らない。tree-gen のような既存ツール、Sketchfab 等の CC モデル、施主による image-to-3D を使う。手続き生成が向くのは建築・橋・台座など幾何学的なもの

### 2-2. スキャンモデルの後処理は「彫り」を壊す
- 平滑化を強くすると「溶けたみたい」になる。デシメートは細かい彫りを消す(ratio 0.5 で顔が消えかけた)
- テクスチャを剥がすと顔の特徴が消える(スキャンは色で顔を表現している)
- 顔の変形(目・鼻の押し出し)は「目がおかしい」「鼻が取って付けたみたい」になる → 全て元に戻した
- 法線マップの `Strength` が元データで 0.3 だった。いくら彫りを強めても最後で 7 割カットされていた → **元データの設定を最初に数値で調べる**
- **教訓**: スキャンから「美しい仏像」は作れない。磨き(amida_polish)までが限界。それ以上は image-to-3D へ

### 2-3. PBR マテリアルの落とし穴
- metallic ≥ 0.7 だとベースカラーのテクスチャがほぼ見えなくなる
- ベージュの空(PMREM 環境)を鏡面反射すると、金属も水も白飛びする → フレネルの自発光、または roughness を上げる
- 「錆びたような斑」は AO ベイクや法線の陰影。**施主が求めるのは均一な金一色**(`PED_GOLD=(0.85,0.62,0.20)`, metallic 0.72, roughness 0.52, 弱い emission)。台座と像は同じマテリアル定義にする
- `blur()` が負の値を切っていて法線が壊れた → 符号付きの `blur_signed` を使う
- 金一色にしても metallic 0.9 前後だと、空の青が映って**顔が青緑に濁る**(9/3)。metallic 0.75 / roughness 0.48 で解消。金箔の皺の法線は 0.3 混ぜると粒に見えてムラ扱いになる → 0.12 まで落とす

### 2-3b. 蓮の花弁の発光と「外面が真っ暗」(9/3)
- 花弁を厚みなし(両面描画)にしたら、開いた外輪の**外面が真っ暗**になった。法線は外向きで正しい。
  原因は「開き角 70° 超の花弁の外面は床を向くので、太陽も空の光も当たらない」こと。旧版は一様な発光 0.42 で隠れていた
- 切り分けの順番: 片面描画 → 法線マップ外し → 発光×3 → 発光マップ外し。**発光マップを外して光れば、マップの値が低い**だけ
  (三択のスクショを 1 枚に並べて 1 回で見る)
- 対処: 発光マップの下限を 0.22 に上げて花弁全体を淡く光らせ、根元 1.0 へ向けて明るく。脈は逆光の葉のように少し暗く
  発光係数は three.js 側 `PETAL_GLOW`(0.75)。雄しべの発光は 1.4 だと白飛びして金に見えない → 0.6
- glb の accessor の min/max はノード変換前のローカル座標。寸法はノード行列を掛けて出す(蓮は直径 1.28m)
- ギャラリーは最初の品目(12MB の如来)の読み込み中に別の品目へ切り替えると、遅れて届いた如来が重なって写る → `show()` にトークンを入れて捨てる

### 2-3c. 光と空気(空・靄・ブルーム・水面反射)の落とし穴(9/3)
- **ブルームを輝度しきい値で選ぶと、日向の金の地面全体が滲んで画面が白飛びする**。発光チャンネル(MRT の `emissive`)だけを
  ブルームに通す。水面の反射を emissive に載せると水面全体が滲むので、水は `MeshBasicNodeMaterial` の colorNode に置く
- 物理空(SkyMesh)は西日 7° だと全面ベージュ。turbidity / rayleigh をいじっても変わらない → 勾配ドーム(天頂 淡い瑠璃・地平 金・西に光)を
  自前で描き、PMREM もそこから焼く
- 金の地面は metalness 0.45 / roughness 0.55 だと西日の照り返しが白い塊になる → roughness 0.68
- `reflector()` の反射面は target の +Z が法線。geometry.rotateX した水面には `target.rotateX(-π/2)` が要る
- 砂のテクスチャは 1.6m ごとの繰り返しが「規則性」として見える → 同じテクスチャを角度・縮尺違いで三重に貼り、ワールド座標ノイズで切り替える
- 斜面に砂紋(横縞)入りの砂を貼ると地層に見える → 斜面用は砂紋なしの版を分ける

### 2-3d. 宝石(透過ガラス)の落とし穴(9/4、七重羅網で 8 回やり直し)
- 濃い base color + 発光の宝石は「色付きの不透明な樹脂」= プラスチックに見える。光沢を上げても直らない。**宝石は透過(transmission 1.0)+厚みによる吸収(attenuation)で色を付ける**
- 吸収距離が短い(0.05)と黒く濁る。0.15〜0.35 で「明るい色ガラス」。淡い色にしたければ吸収色を明るく、距離を長く(桜・水・藤 = 0.35)
- ルビーが桃色に見えるのは**表面の映り込み(空の白)が混ざる**から。透過色・吸収だけでなく specularColor まで赤く染めて初めて「深紅」と言われた
- サファイアは「透明感」= 縁が透けて厚い所だけ濃い → 透過色を明るく、吸収距離 0.15
- 空間側で名前 `*_gem` を読み込み時にプリセットで上書きする方式なので、glb 側の色は当てにならない。プリセットに無い名前は Blender の色のまま

### 2-8. 七重羅網(9/4、構造で 5 回やり直し)
- 「並木の上空に広く張る」は参考図と全く違った。施主の図は**池の上に花綱(スワッグ)のように垂れる**もの。参考図があるときは構造を先に合わせる
- 「もっと垂れ下がる」を 4 回言われた。垂れは間隔の 30〜46% の**懸垂線(電線)**で、支点は区画の始端だけにして区画をまたいで一本の弧にする。最初の弧の深さ(1.2m)は施主基準で「ほぼ直線」
- 瓔珞は 20m 下から見上げるので、地上で作った寸法の **4.4 倍**が「読める」大きさ。装飾品は視距離で倍率を決める

### 2-9. 宝樹(9/4)
- ルビー・サファイアの飾りは「派手」。施主の好みは**淡くて優しい色**(桜色・水色・藤色)、葉も淡い金
- 樹皮テクスチャを残したまま金属にすると幹が黒ずむ(暗い樹皮色が反射に乗る)。**幹は無地の金**にする
- 外周 180 本に 90k tris の飾りは重すぎる。本数の多い木は吊り下げ点 40 に絞る

### 2-10. 楼閣の精巧化(9/5)
- 部材を 2,256 → 5,072 個にしたら Blender の生成が 25 分かかる。`bpy.ops.mesh.primitive_*` は 1 回ごとにシーン全体を再計算するので、部材数に対して二乗で遅くなる。**細部は Batch(make_ramou)のように一つのメッシュに詰める**か、生成は裏で回して待つ
- 灯籠の発光 3.0 はギャラリーのブルームで白飛び。1.1 で「灯っている」に見える
- 長押の宝石鋲を赤珠と瑠璃の交互にすると「青い点」が並ぶ。施主は青のラインを嫌うので**赤珠と真珠**に
- 八角の屋根の丸瓦は放射状に走らせ、頂に近づいて詰まる分は一列おきに途中で止める

### 2-4. 形の破綻は数値で先に見つける
- 蓮華座の花弁が重なった(幅 > 間隔)、内側の輪が外側を突き抜けた、返花が浮いた(8/28)
- 八角楼の 2〜3 階が 0.95m / 0.4m 浮いていた、階段が八角形の角に当たっていた(8/23)
- 橋の接合、宝樹の原点ずれ(takara_tree は原点から約 (-9, -11) ずれている)
- **教訓**: 花弁数・幅は弧の間隔から計算する。段の接合は bpy で頂点のワールド座標を出して判定。スクショを何枚も撮って目で探さない

### 2-5. 施主の美的な要求の傾向(繰り返し言われたこと)
- 「もう少しテクスチャを細かく」「細部まで作り込んで」「誰が見ても感嘆するくらい」→ 常に **最初から最大の作り込み**で出す
- 「模様ではなく、材質の細かな描写を」→ 幾何学模様のテクスチャは「気持ち悪い」と言われる。金箔・槌目・磨きなど**材質感**のテクスチャにする
- 「花びらが尖りすぎ」→ 丸みのある先端(`round_tip`)
- 「クワガタみたい」→ 細くて反りの強い花弁は虫に見える。幅広・低カールに
- 「蓮が大きすぎる」(9/1)→ 車輪大 = 直径 1m 前後。手前の主役でも 1.2m まで(9/4 は倍率 1.2〜2.6 = 直径 1.5〜3.3m のばらつきで通った。大きさより**ばらつき**が効く)
- 「サイズは全部同じ?」(9/4)→ ±16% の乱数は「同じ」に見える。倍率で 2 倍以上の幅を取り、小さめ多め・大株少なめに偏らせる
- 「淡い光を放つように」(9/3)→ 淡いと言われても、結局「もっと強く」「もっと光量を」と 3 回上げて発光 1.6 + ブルーム 1.4 に落ち着いた。**光は最初から強めに出す**
- 「粗い」「もっと細かく」(9/3、砂で 3 回)→ 粒は最初から 3〜4cm まで細かく。**横縞(砂紋)は地層に、繰り返しは規則性に見える**ので、斜面は砂紋なし+アンチタイリングを最初から入れる
- 「規則性があって不自然」→ 施主はタイルの繰り返しを一目で見つける。テクスチャを繰り返す面は必ず角度・縮尺違いの重ね貼りにする
- アルカイックスマイル、険しい顔は NG(ただし顔の変形はそもそも不可 → 2-2)

### 2-6. MakeHuman(MPFB2)素体から仏像を組む試み(9/2、施主が断念)
- 人体素体 → 結跏趺坐 → 螺髪 → 衣、の手順で頭までは「とりあえずおけ」に到達したが、一往復 4 分 × 約 40 往復かかった
- 目を閉じる: メッシュ操作(穴・パッチ・溝)はすべて失敗。リグの瞼ボーンを回すのが唯一通った方法。目の縁は細い管で線を足す
- 螺髪: 表面サンプル + 詰め込み + 緩和で敷き詰める。まばら・はみ出し・耳にかかる、で三度組み直し。境界は黒い管で縁取る
- もみ上げの形だけで十回近く。「太い/細い/尖り/丸み」は 1〜2mm 単位の指示になる
- 体: 全身の凸包で衣を作ると「三角錐」になる。胴・腕・膝を別体積で作る。手を包んだ布の切り口に管を通すと「縄跳び」になる
- **教訓**: 木・楼閣・橋は一日で通るが、仏像は「人が違和感を覚える点の積み重ね」で、言葉と数字では届かない。
  次に仏像を作るなら、image-to-3D(Tripo 等)か既存モデルから始め、手続き生成では顔・手を作らない

### 2-7. 仏像の金色化は「色の置き換えだけ」(9/3)
- 法線を強め(0.3→0.85)、金箔の皺の法線を混ぜ、減面(0.7)した版は「チョコレートをかけたようにドロドロ」「螺髪が崩れてる」と却下
- 原型の法線(強さ 0.3)・分割・溶接なしのまま、ベースカラーの写真だけを金一色に替えた版で解消(18万tris・12MB)
- metallic 0.9 の鏡面寄りにすると、空の青が映って顔が青緑に濁る。台座と同じ metallic 0.75 / roughness 0.48 に留める
- **教訓**: 「表面の色を変えて」は文字どおり色だけ。法線・粗さ・減面のどれも触らない

| 失敗 | 原因 | 対処 |

| 砂が荒い、波が小さい、池が小さい(8/25) | 初回の値が控えめすぎた | 粒 2px、池外周 30→38、波 0.16 + 0.045 の二重波 |

| スクショのタイムアウト | 1,100 インスタンスのシーンは swiftshader で 30 秒を超える | viewport 960x600、`screenshot({ timeout: 240000 })` |
| ブルームで画面が真っ白(9/3) | 輝度しきい値のブルームが日向の金の地面全体を滲ませた | `pass().setMRT(mrt({output, emissive}))` で **発光チャンネルだけ**を `bloom()` に通す。水面の反射は emissive に載せない(水面全体が滲む) |
| 空が全面ベージュ | SkyMesh は西日 7° だと turbidity / rayleigh を変えても暖色一色 | 勾配ドーム(天頂 淡い瑠璃・地平 金・西に光)を TSL で描き、PMREM もそこから(sky.ts) |
| 水面に何も映らない | 環境反射を切っていた(ベージュ空対策) | `reflector({resolutionScale: 0.5})` を `MeshBasicNodeMaterial` の colorNode に。target の +Z が法線なので `target.rotateX(-π/2)` |
| 蓮の光が水に映らない | 光のスプライトは後処理の外なので反射に滲まない | 水面下に鏡像のスプライトを置き、半透明の水を透かす。水面の光輪も広げる |
| ギャラリーで如来が蓮に重なって写る(9/3) | 最初の品目(12MB)の読み込み中に切り替えると、遅れて届いた方も追加される | `show()` にトークンを持たせ、古い読み込み結果を捨てる |
| 撮影の並列実行が全部 exit 1(9/4) | 3 本同時に chromium を立てるとプロキシ/起動で落ちる | 順に実行するか `sleep 5` ずつずらす。exit 0 でもファイルが無いことがある → `ls` で確認 |
| 開いた花弁の外面が真っ黒 | 外面が床を向くので空も太陽も当たらない。法線は正しい | 発光マップの下限を上げる(2-3b) |

## 4. 仏像づくりの経緯(同じ轍を踏まないための年表)

1. Sketchfab のスキャン(CC-BY-SA)を金に塗装 → 「木彫のまま」感、斑が残る
2. 「磨き」処理(CLAHE・法線強調)で amida_polish → ここが後処理の上限。**アセットとして保存済み**
3. メタボールで自作 → 即却下
4. 蓮華座を合体させた amida_full → 色統一の要求で全マップ剥がし、金一色。顔の輪郭は出せず「直ってない」
5. GitHub で他手法を調査 → 施主「イラストとキャラクターシートから作るやつはないの?」
6. キャラクターシート(正面・側面・背面の切り出し 1024²、白背景)を用意 → 環境から API 不可 → **Tripo で施主が生成中**
7. 届いたら: 数値で寸法確認 → 金一色マテリアルに統一(2-3 の値)→ 最適化 → ギャラリー登録 → ATTRIBUTION.md → 承認後に中島の蓮華座(scale 3, ISLAND_TOP)へ

**次に仏像を触るときのルール**: 顔の形状は絶対にいじらない。マテリアルは台座と同一。「はっきりさせて」は法線の Strength とライティングで応える。無理なら無理と言う。

## 5. 日記・リポジトリ運用の事故

| 事故 | 原因 | 再発防止 |
|---|---|---|
| Obsidian Git の同期で 8/21 のアセットが消えた | 日記と本体が同じリポジトリだった | 日記は `pipi-0078/jodo_diary` に分離。本体に日記を置かない |
| iPhone の Obsidian で `Unsupported dircache version: 3` | isomorphic-git は index v2 のみ。Mac と .git を共有していた | 端末ごとに別クローン、Mac は `git update-index --index-version 2` |
| iPhone で author 未設定、認証ダイアログが出ない | プラグイン設定に name/email、PAT が必要 | `.obsidian/` は gitignore(PAT を含む)。**pull してから commit**、auto-commit は切る |
| jodo_diary を一時 Public にした | クローンのため | 用が済んだら **Private に戻す**(9/1 時点でまだ Public の可能性あり) |
| デプロイ失敗のメール | 上記 N8AO の peer dep | プッシュ前に `npm ci` 相当で通ることを確認 |
| スマホで pull しても記事が降りてこない(9/4) | Obsidian Git の「Author name / email」が未設定で、pull 前の自動コミットで処理が止まっていた | まず GitHub 側にファイルがあるかを API で確認して切り分ける。あればスマホ側。プラグイン設定に name / email を入れる |
| セッションから jodo_diary へプッシュできない(9/3) | リポジトリ権限が本体だけ | 記事は先に SendUserFile で渡し、施主に「jodo_diary を追加して」と言ってもらってからプッシュ(→ 1.) |

## 6. 施主とのやり取りで学んだこと

- 施主は数値より**見た目の一言**で判断する(「浮いてない??」「クワガタみたい」「厚化粧」)。その一言は正確なので、疑わず原因を数値で探す
- 「正直に答えてね?」と聞かれたら、出典や限界をそのまま言う(Sketchfab 由来であることは隠さない)
- 大きな作業の途中でも「今日はここまで」で日記(x-worklog)を書く。失敗も日記に率直に書く。施主はそれを読み物として楽しんでいる
- 報告は要点のみ。作業ログの実況はしない
